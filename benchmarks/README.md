# Recorded benchmark artifacts

This directory holds **previously executed** evaluation experiments, committed so
the public read-only Streamlit deployment can display real results without running
anything (the Cloud demo has no dense/rerank extra and an ephemeral filesystem).

Each `*.json` file is a full experiment record produced by the local runner via:

```powershell
uv run rag-workbench eval record <experiment-id> --name <descriptive-name>.json
```

The `record` command trims each query's ranked trace to a few items and truncates
excerpts (aggregates, candidate-pool metrics and per-query metrics/diagnostics are
kept complete); unjudged queries keep no trace. A note inside each file states the
truncation. Use `--full` to write the untrimmed record instead.

## Record schema and evaluation policy

These artifacts use record **schema version 2**. Two policies are recorded in every
file so a result cannot be misread:

- **Unjudged queries are skipped before retrieval.** A query with no relevance
  judgments can never produce a metric, so the runner does not retrieve it at all
  (`skip_unjudged`, default on). SciFact's 809 unjudged queries are therefore
  counted in `queries_excluded_no_qrels` but never retrieved; SciFact's
  `queries_retrieved` is 300, not 1109. Latency statistics cover only the queries
  that actually ran.
- **Candidate recall is a first-stage property.** The runner keeps four
  quantities explicit: the first-stage candidate depth (`candidate_depth`, which
  is also the candidate-recall depth), the reranker input (`rerank_candidates`,
  defaulting to the pool depth), the final result count (`top_k`), and the pool
  it measures. `candidate_recall@N` is measured on the rerank-free first-stage
  retrieval at `candidate_depth`, so reranking — which only reorders that pool —
  never changes it. When `rerank_candidates < candidate_depth` the reranker
  scores only part of the pool, but the candidates beyond its input are still
  counted in candidate recall rather than silently discarded.

All numbers below were **measured in this project** on one Windows machine (CPU),
Python 3.12, `sentence-transformers/all-MiniLM-L6-v2` (384-d) and
`cross-encoder/ms-marco-MiniLM-L6-v2`. Retrieval depth is a **chunk** count.

| `scifact-dense-minilm.json` | BEIR SciFact | dense (MiniLM) | depth 100 |
| `scifact-hybrid-rrf-minilm.json` | BEIR SciFact | hybrid (RRF) | 200 candidates |
| `scifact-bm25-pool20-baseline.json` | BEIR SciFact | BM25 (`or`) | depth 20 — matched rerank baseline |
| `scifact-bm25-pool20-rerank-minilm.json` | BEIR SciFact | BM25 (`or`) + rerank | same 20-passage pool as the baseline |

## Recorded answer demonstrations (`recorded_answers/`)

The sibling directory `benchmarks/recorded_answers/` holds **Phase-5 answer
artifacts**, recorded by:

```powershell
uv run rag-workbench answer record --profile <profile-id> `
  --dataset answer-quality/legal-contracts-answers --query-mode or --max-evidence 6 --seed 0
```

It contains `answer_demo` JSON files (the full answer record: question, selected
evidence, generated answer, claims/citations, deterministic verification,
retrieved-vs-selected context, diagnostics, model identity and timings) and one
`answer_quality` report **per configuration**. All carry `source="recorded"`, so the
read-only deployment can never present them as live inference.

The directory intentionally holds more than one report. The **original** Phase-5
run (`aq-20261015T225614.json`) is preserved unedited, and later runs record a
controlled configuration comparison (baseline vs. an alternative prompt; and
`max_evidence` 4/6/8). Multiple reports coexist because they are different
experiments, not revisions of one result: the API's newest-report endpoint returns
the recommended configuration while `/v1/answer-quality-reports` (and the Answer
Laboratory) lists them all for side-by-side comparison. See the README §16 for the
metrics and their honest interpretation, including the preserved `aq-007` failure.

`--seed` fixes sampling so a repeated configuration is reproducible; omit it for
normal sampling. Add `--no-demos` to record only the aggregate report when sweeping
configurations.

## Recorded scaling baselines (`recorded_scaling/`)

The sibling directory `benchmarks/recorded_scaling/` holds **Phase-6 scalability
artifacts**: bounded, single-machine measurements of indexing and BM25 retrieval
cost at several corpus sizes over a deterministic synthetic corpus. They are
produced by:

```powershell
uv run rag-workbench scaling run --documents 100,1000,5000 --depths 10,50,100 --record
```

Each `scale-*.json` file records the corpus configuration and fingerprint, the
execution environment (Python, platform, CPU, package versions), the code revision
with its working-tree state (`git_commit`, `git_dirty`, `provenance`), and one
workload block per corpus size with ingestion throughput, on-disk footprint (SQLite
file, FTS5 shadow-table bytes and source bytes), BM25 latency percentiles by
candidate depth, and a memory measurement. The memory fields are deliberately
distinct: `rss_mb` is one instantaneous process-RSS reading, `sampled_peak_rss_mb`
is the maximum of periodic process-RSS samples (both need `psutil`,
`uv sync --extra profiling`), and `tracemalloc_peak_mb` is a Python-managed
allocation peak that is **not** total process memory. Without `psutil`, process RSS
is reported as not measured rather than inferred from the heap.

Every artifact carries `source="recorded"` and a `limitations` list, so the
read-only deployment shows real measurements without presenting them as a
production throughput claim. Historical artifacts that named the wrong code
revision are preserved under `superseded/` (the loader ignores that subdirectory);
the live artifacts were regenerated against committed code. The directory holds
more than one artifact on purpose: the primary `paragraph`/220 baseline and a
`fixed_token`/512 run demonstrate that **chunking strategy, not the token budget,
dominates chunk count**. See [`docs/scaling_to_10m.md`](../docs/scaling_to_10m.md)
and [`docs/case_studies.md`](../docs/case_studies.md) for the interpretation.

`load/` holds an **optional** Locust definition that exercises the read-only API
endpoints. Locust is an optional extra (`uv sync --extra load`), so it is never
installed by the core sync; run it with
`uv run --extra load locust -f benchmarks/load/locustfile.py --host http://127.0.0.1:8765`
(or `uv run --with locust ...` without changing the environment).
The built-in `rag-workbench scaling load-test` harness needs no extra install.
